# Qt issues encountered in SunPlayer

Last checked: 2026-10-18. This is an evidence index, not authorization to patch Qt or change
dependencies. Approved application fixes are identified explicitly below. Distinguish matching upstream
reports, source limitations and unclassified application/platform behavior.

## Windows Fluent scrollbar contrast

User reports the scrollbar appears during scrolling but is practically invisible;
hover makes it easier to see. This matches
[QTBUG-138957: Fluentwin3ui: adjust the ScrollBar visibility in dark mode](https://qt-project.atlassian.net/browse/QTBUG-138957).
Tracker status: Reported, no resolution or fix version.

Qt 6.11.1 Fluent uses Fusion's fallback ScrollBar. Its thumb uses palette.mid
normally and palette.dark while pressed, with 0.75 active opacity. Hiding while
idle is intentional; insufficient contrast while scrolling is the reported issue.
The accepted #181818 canvas improves the general appearance but is not a fix.

The user approved the minimal workaround: a palette adjustment on all six
explicit QML scrollbars, reusing palette.text for mid/dark on Windows. The shared
stock AppScrollBar wrapper holds this rule; it preserves interaction and fade.
It is implemented; installed Windows appearance remains manual acceptance. AlwaysOn
would change hiding, not repair contrast. Avoid application-wide palette changes.

Sources: [Fusion scrollbar](https://github.com/qt/qtdeclarative/blob/v6.11.1/src/quickcontrols/fusion/ScrollBar.qml),
[Fluent fallback](https://github.com/qt/qtdeclarative/blob/v6.11.1/src/quickcontrols/fluentwinui3/CMakeLists.txt),
[palette customization](https://doc.qt.io/qt-6/qtquickcontrols-fluentwinui3.html#palette).

## Linux portal theme ignores the explicit dark request

The AppImage uses Qt 6.10.2 and selects xdgdesktopportal when a live FileChooser
portal is available, unless the environment explicitly selects another theme.
The user reports light controls/dialogs while desktop accent colors are retained.

The portal theme forwards palette/font/theme hints to its base theme, but does
not override or forward requestColorScheme(). The inherited base implementation
ignores the requested scheme. The omission remains in exact Qt 6.12.0 and dev
source examined on the date above. Desktop palette inheritance and honoring an
application appearance request are separate behaviors. Portal-owned file dialogs
also have their own desktop appearance policy.

Closest related report:
[QTBUG-127028: QStyleHints::colorScheme doesn't match actual palette](https://qt-project.atlassian.net/browse/QTBUG-127028),
Reported with no fix version; its flatpak/Fusion example shows dark scheme/light
palette. No exact public ticket or Gerrit change for the portal wrapper's missing
request forwarding was found. Do not label the related ticket an exact match.
No workaround or dependency update has been applied.

Sources: [6.12.0 portal header](https://github.com/qt/qtbase/blob/v6.12.0/src/plugins/platformthemes/xdgdesktopportal/qxdgdesktopportaltheme.h),
[portal implementation](https://github.com/qt/qtbase/blob/v6.12.0/src/plugins/platformthemes/xdgdesktopportal/qxdgdesktopportaltheme.cpp),
[base request implementation](https://github.com/qt/qtbase/blob/v6.12.0/src/gui/kernel/qplatformtheme.cpp).

## Touchpad rounded-pixel stutter

The prior trace included phased zero-pixel/nonzero-angle touchpad updates,
matching [QTBUG-149567](https://qt-project.atlassian.net/browse/QTBUG-149567).
The tracker is Closed/Fixed and lists 6.8.10, 6.12.0 and 6.12.1. During the
original investigation tagged source and tracker metadata differed: verify the
[actual fix](https://github.com/qt/qtdeclarative/commit/281a769a15ad73fad04058f50c11e85063eeb071)
in any proposed dependency update rather than relying on metadata alone.

This does not establish the cause of all perceived stiffness or missing release
inertia. A stock Qt comparison felt equally stiff, and the user also observed
missing inertia in Chrome. Accepted decision: retain Qt defaults, no Qt patches,
custom scroll physics or sensitivity overrides. See
[original investigation](2026-10-18-jellyfin-client.md#actual-device-comparison-and-final-decision).

## Windows HDR display selection with mixed DPI / hybrid GPUs

[QTBUG-149927](https://qt-project.atlassian.net/browse/QTBUG-149927) reports D3D11
scRGB/HDR10 silently falling back to SDR on an HDR screen at 300% scaling.
The report also identifies a separate adapter/output mismatch on hybrid GPUs.
The user identifies earlier project investigations on August 24 and September 19.
Tracker status on October 18: Reported, no resolution or fix version.

The old output6ForWindow code multiplies global Qt window geometry by DPR,
which can select the wrong DXGI output in mixed-DPI layouts. This calculation
remains in Qt 6.11.1 and 6.12.0 release tags. However, current dev and the 6.12
maintenance branch now prefer MonitorFromWindow(HWND):
[37a9bf670e: QRhi: fix detection for HDR in mixed-DPI monitors](https://github.com/qt/qtbase/commit/37a9bf670e422daa20c1806fc873c27b35fb287d).
Its commit requests a 6.12 backport. No released fixed version was verified;
tracker status alone does not reflect this source change. Do not infer that
this fixes the separate hybrid-GPU adapter selection variant.

Reported diagnostic workarounds are QT_ENABLE_HIGHDPI_SCALING=0 for the DPI
variant and QT_D3D_ADAPTER_INDEX selecting the output-owning adapter for the
hybrid-GPU variant. These are not SunPlayer defaults or approved product fixes.
No native Windows build/test or environment change was performed here.

Sources: [6.11.1 source](https://github.com/qt/qtbase/blob/v6.11.1/src/gui/rhi/qdxgihdrinfo.cpp),
[6.12.0 source](https://github.com/qt/qtbase/blob/v6.12.0/src/gui/rhi/qdxgihdrinfo.cpp),
[current maintenance source](https://github.com/qt/qtbase/blob/6.12/src/gui/rhi/qdxgihdrinfo.cpp).

## Linux card hover: reproduced chrome-overlay interaction

The user reports both AppImage and debug builds with a mouse: card hover does
not highlight, pressing can highlight, and highlighting can remain stuck.
The isolated real JellyfinPoster enters/leaves hover correctly on Qt 6.10.2.
The full shell with CSD enabled reproduces missing card hover.

Qt hover trace reaches the full-window ClientSideWindowChrome at z=100 and
never reaches the card beneath. Its full-window HoverHandler is enabled with
Linux CSD; Windows native chrome leaves it disabled. Disabling only that handler
in the same fixture restores card hovered=true on entry and false on exit.
Setting blocking=false explicitly does not help (it is already the default).
The examined Qt delivery code marks a hovered handler's item as the hovered
leaf and stops visiting lower siblings, separately from the blocking check.
This is a demonstrated CSD-overlay interaction, not a generic Linux theme issue.
No exact upstream ticket has been established.

A temporary experiment scoped that existing handler to its titleBar parent.
Added fixture assertions then observed real card hover enter/leave with CSD,
and the full Fusion shell suite passed (4 passed, 0 failed), including existing
chrome/controls inactivity coverage. This is the candidate minimal fix: let the
chrome observer cover chrome rather than browser content; retain PlayerPage's
existing content observer. The user then approved implementation: the handler is now scoped to titleBar,
and retained fixture assertions cover enter, press/leave/release and re-entry.
This corrects the application layout instead of patching Qt.

Temporary standalone probes were removed; the regression assertions remain in
the normal shell test. No Qt patch or synthetic hover delivery was introduced.
Sources: [HoverHandler contract](https://doc.qt.io/qt-6/qml-qtquick-hoverhandler.html#blocking-prop),
[Qt 6.10.2 delivery](https://github.com/qt/qtdeclarative/blob/v6.10.2/src/quick/util/qquickdeliveryagent.cpp).

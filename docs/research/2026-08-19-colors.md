Your instinct is basically right, with one important distinction:

**SunPlayer should own source interpretation + tone mapping + high-quality gamut mapping to the usable display color volume. The OS/compositor should own the final color-space/profile/calibration transform to the physical panel.**

Those are not duplicate jobs. Windows explicitly says its Advanced Color display pipeline performs color-space conversion/calibration but merely numerically clips colors outside the display gamut; applications wanting better gamut mapping must do it themselves. Apple likewise documents an “own tone mapping” EDR path, and with `CAMetalLayer.edrMetadata == nil` macOS does no extra tone mapping before the display and may clip values above available EDR. ([Microsoft Learn][1])

That is also almost exactly the architecture SunPlayer has already settled on in ADR 0013.

## The libplacebo distinction is the key

The current target in `LibplaceboRenderContext.cpp` is:

```cpp
target.color.primaries = PL_COLOR_PRIM_BT_709;
target.color.transfer = PL_COLOR_TRC_LINEAR;
// target.color.hdr.prim unset
```

There are two different concepts hiding here.

`target.color.primaries` describes the **numeric RGB coordinate basis of the target image**. BT.709 is correct for SunPlayer's linear-sRGB/extended-sRGB intermediate. An FP16 BT.709-basis RGB space is not inherently limited to the BT.709 triangle: negative and >1 components let it represent chromaticities outside BT.709.

`target.color.hdr.prim`, despite the slightly HDR-centric “mastering display primaries” naming, is what libplacebo's color mapper actually uses as the **target gamut/color volume**. In pinned libplacebo 7.360.1, gamut mapping is literally initialized as:

```cpp
.input_gamut  = src.hdr.prim,
.output_gamut = dst.hdr.prim,
```

When `hdr.prim` is absent, libplacebo inference fills it from the nominal `.primaries`, which is why the current BT.709 coordinate basis accidentally becomes a BT.709 gamut restriction. SunPlayer already records exactly this limitation.

So the conceptual target should be:

```text
target.color.primaries = BT.709          // numerical RGB basis
target.color.transfer  = LINEAR          // SunPlayer intermediate
target.color.hdr.prim  = display gamut   // gamut-mapping boundary
```

Do **not** change `.primaries` to Display P3/BT.2020 while continuing to hand the resulting numbers to a surface declared extended-linear sRGB. That would describe the numerical values incorrectly.

There is good upstream precedent here. mpv exposes `target-prim` and `target-gamut` separately and writes its target gamut into `target.color.hdr.prim`.  Even more directly, current post-7.360.1 libplacebo's D3D11 scRGB work declares the output as BT.709 primaries while separately propagating target `hdr.prim`.

One thing I corrected while researching: pinned 7.360.1's `PL_COLOR_TRC_LINEAR` path **does preserve negative output components** because linear delinearization returns before the generic clamp. So your current linear intermediate can carry real wide-gamut scRGB coordinates.  The newer `PL_COLOR_TRC_SCRGB` is not necessary here—and arguably isn't the right semantic description anyway, because SunPlayer's internal `1.0` means active SDR/reference white, not scRGB's fixed Windows 80 nits.

## The common pipeline I would preserve

The architecture you already have is good:

```text
decoded source
  │ source primaries / transfer / matrix / HDR metadata
  ▼
libplacebo
  ├─ decode to linear light
  ├─ source HDR interpretation
  ├─ tone-map to current usable luminance volume
  └─ perceptually gamut-map to current usable display gamut
  ▼
FP16 linear BT.709-basis composition
  1.0 = current platform SDR/reference white
  values <0 and >1 permitted
  │
  ├─ video
  ├─ sRGB UI
  └─ subtitles
  ▼
final platform encoding
  ▼
OS/compositor profile + calibration transform
  ▼
physical display
```

SunPlayer's existing virtual-target math should remain. It intentionally gives libplacebo a target where `1.0` becomes the active reference white and the maximum is `P/W`, letting it tone-map to the display rather than allowing the compositor to ugly-clip highlights.

The new missing quantity is essentially:

```text
targetGamut = reliable usable display primaries
```

alongside the existing `referenceWhite`, `minimumLuminance`, and `targetPeakHeadroom`.

## Platform-by-platform

| -------------------------------- | ------------------------------------------------------------------ | ------------------------------------------ | ----------------------------------------------------- |
| Windows HDR Advanced Color       | physical/native gamut, peak `P`, white `W`                         | FP16 scRGB, **× W/80 exactly once**        | Windows DWM/display pipeline                          |
| Windows SDR Advanced Color / WCG | physical/native gamut, headroom 1                                  | FP16 scRGB, **no W/80**                    | Windows DWM/display pipeline                          |
| Windows without Advanced Color   | BT.709/sRGB, headroom 1                                            | ordinary SDR sRGB                          | none unless SunPlayer implements post-composition ICC |
| macOS EDR                        | known/safe display gamut, current EDR headroom                     | RGBA16F extended-linear sRGB, **no scale** | Core Animation/ColorSync                              |
| macOS SDR                        | gamut supported by chosen output encoding                          | tagged SDR/wide-gamut layer                | Core Animation/ColorSync                              |
| Wayland CM v2 HDR                | preferred `target_primaries`, preferred target luminance/reference | current BT.2020/PQ final encoding          | compositor                                            |
| Wayland CM v2 SDR fallback       | limited by selected SDR surface encoding                           | managed gamma/sRGB surface                 | compositor                                            |

### Windows HDR Advanced Color

This one is the cleanest.

Microsoft defines DWM's canonical HDR composition space as FP16 linear BT.709/scRGB and explicitly says it can represent colors outside sRGB with values outside `[0,1]`. It exposes the panel's physical color volume through `AdvancedColorInfo`: red/green/blue primaries, white point, min/max luminance, full-frame luminance, and SDR white. Microsoft says that data should be used to configure application tone and gamut mapping. ([Microsoft Learn][1])

So:

```text
libplacebo hdr.prim = AdvancedColorInfo native primaries + white
W = SdrWhiteLevelInNits
P = usable MaxLuminanceInNits
headroom = P / W
```

Then after the whole composition:

```text
Windows scRGB = workingRGB × W / 80
```

Exactly as SunPlayer already does. Microsoft explicitly specifies this adjustment for applications that composite SDR and HDR into one FP16 surface. ([Microsoft Learn][1])

Windows then turns correctly tagged scRGB into the display's calibrated output. Do not fetch/apply the display ICC yourself on this path. Windows specifically advises Advanced-Color-aware apps not to directly use display ICC profiles because the system owns that stage. ([learn.microsoft.com][2])

### Windows SDR Advanced Color / WCG

This is the subtle mode that needs to remain separate from HDR.

Microsoft says SDR Advanced Color is **display-referred**, whereas HDR Advanced Color is scene-referred:

```text
SDR Advanced Color: 1.0 = display reference/max white
HDR Advanced Color: 1.0 = 80 nits
```

And they explicitly say SDR reference-white scaling applies only to HDR displays. ([Microsoft Learn][1])

Therefore:

```text
WCG SDR:
    target luminance headroom = 1
    target gamut = native display primaries
    final scale = 1
```

You can still have negative or >1 RGB components here for **wide gamut**, even though luminance headroom is one. “component >1” and “brighter than SDR white” are not equivalent in an extended BT.709 coordinate system.

This is why I think `AdvancedColorKind` needs to become an explicit piece of SunPlayer presentation state rather than being collapsed to the current `hdrActive` bool. Your Windows provider currently reads `CurrentAdvancedColorKind()` but stores only whether it equals HDR, plus luminance values; it doesn't retain WCG or native primaries.

So most of the infrastructure is there, but this state representation is too lossy for the final color pipeline.

### Windows with no Advanced Color

Here the elegant “OS owns everything downstream” model stops working.

Microsoft is explicit: legacy SDR DirectX output is assumed sRGB and **isn't automatically display-profile color managed**. An FP16 scRGB surface used on a standard display is downconverted by clipping values outside `[0,1]`. ([Microsoft Learn][1])

The current `UnmanagedSrgb` policy in ADR 0013 is therefore correct and honest:

```text
target gamut = BT.709
headroom = 1
output = sRGB SDR
```

If “completely color-correct on every arbitrary legacy Windows monitor” becomes a requirement, there is no zero-code OS solution. SunPlayer would need the deferred third mode:

```text
complete linear composition
  -> application display-ICC/WCS transform
  -> physical-display RGB
```

And that transform must encompass UI/subtitles as well as video. Doing ICC only inside libplacebo would be wrong.

I would keep that deferred unless legacy calibrated SDR monitors are genuinely an important target.

## macOS

Your present luminance model is right.

Apple's own “perform your own tone mapping” recipe is almost SunPlayer verbatim: RGBA16F `extendedLinearSRGB`, EDR enabled, with `1.0` corresponding to maximum SDR brightness rather than a fixed 80-nit level. ([Apple Developer][3])

And `edrMetadata == nil` is exactly what you want when libplacebo owns the tone mapper: Apple says nil causes no system tone mapping and values beyond current EDR capability may simply clip. ([Apple Developer][4])

So your current use of:

```text
1.0 = SDR white
max = NSScreen.maximumExtendedDynamicRangeColorComponentValue
no Windows-style scale
```

is conceptually correct. The existing Mac provider already observes current and potential EDR headroom.

The missing bit is gamut.

Unlike Windows and Wayland, macOS doesn't give you one obvious “native r/g/b xy” property alongside EDR headroom. It does, however, expose `NSScreen.colorSpace`, and ColorSync exposes the associated ICC profile and facilities to inspect whether it is matrix-based/wide-gamut and inspect profile tags. ([Apple Developer][5])

There are two reasonable policies.

The higher-accuracy route is to derive a usable raw target gamut from the active display profile when that profile can cleanly provide one. This is more work than it first appears because ICC colorant tags are in ICC PCS conventions and LUT profiles don't necessarily correspond to one RGB triangle.

The beautifully low-complexity conservative route is Apple's own gamut capability API:

```text
if NSScreen.canRepresent(.p3):
    target gamut = Display P3
else:
    target gamut = BT.709
```

Apple exposes exactly `sRGB` and `P3` through `NSDisplayGamut`, and `canRepresent()` means the screen's color space can represent that gamut. ([Apple Developer][6])

I quite like that as the first macOS policy. It is a guaranteed lower bound, not a guess. You may leave some gamut unused on an unusual AdobeRGB-ish external monitor, but you don't incorrectly invent a larger gamut. Later, exact profile-derived primaries can replace it.

And critically, the final layer stays tagged `extendedLinearSRGB`: Core Animation says that when `CAMetalLayer.colorspace` is set, it performs the necessary color-space transformations during composition. ([Apple Developer][7]) That's the ColorSync/calibration stage you want to preserve.

One macOS edge case remains: an **SDR-only but wide-gamut** external display. If SunPlayer falls all the way back to an ordinary sRGB swapchain, the final encoding itself cannot carry P3. To exploit such a display you need a managed wide-gamut output encoding, rather than merely telling libplacebo that the monitor is P3. That's separate from the HDR/EDR case and worth treating explicitly.

## Wayland color-management-v1/v2

Wayland has the nicest terminology for this problem because the protocol explicitly separates:

> primary color volume = how the pixels are encoded
> target color volume = what is actually displayable

([Wayland][8])

That is almost exactly:

```text
libplacebo target.color.primaries
vs
libplacebo target.color.hdr.prim
```

The preferred parametric description can expose `target_primaries`, `target_luminance`, and reference white. ([Wayland][8])

And amusingly, SunPlayer already parses all of them. `WaylandPreferredDescription` knows `targetPrimaries`, `targetMinimumLuminance`, and `targetMaximumLuminance`; but `displayStateFromWaylandDescription()` currently throws the primaries away when converting to the shared `DisplayState`.

So Linux is probably the easiest place to close the immediate `hdr.prim` bug.

There is, however, one deeper finding concerning ADR 0021.

Your current managed-Wayland policy keeps one stable BT.2020/PQ surface description and lets preferred-description changes affect rendering but not the surface declaration.  That's attractive operationally, but the protocol explicitly says that if the preferred encoding otherwise matches but its target color volume is larger than the content actually needs, the client should create its own parametric image description with the **exact target volume**. ([Wayland][8])

That matters because SunPlayer has already tone/gamut-mapped the composition to a display target. If it then tells the compositor only “BT.2020/PQ, potentially full BT.2020/10,000 nits,” the compositor has less information telling it that the image is already confined to a smaller target volume.

The cleaner semantic model is potentially:

```text
primary/encoding volume:
    BT.2020 + PQ, stable

target/mastering volume:
    the gamut + effective luminance volume SunPlayer mapped into
```

The encoding and swapchain need not change merely because the target-volume metadata changes.

For the current Wayland reference-white bridge, I would expect the target max encoded in that description to be the same virtual quantity you already use with libplacebo:

```text
targetMaxInPQSourceCoordinates = 203 × physicalPeak / outputReferenceWhite
```

because the protocol explicitly requires compositors to anchor differing `reference_lum` values to the same output reference. ([Wayland][8])

That last part is an inference from the protocol plus SunPlayer's 203-nit PQ encoding, so it deserves compositor validation before becoming an ADR. But I think ADR 0021's “never update the surface declaration” is the one existing decision I would now re-examine—not the stable BT.2020/PQ encoding itself.

## What to do when gamut is unknown

I would not use “BT.2020 and hope the OS sorts it out” as the generic fallback.

That maximizes preservation but gives the final color manager colors the display cannot reproduce. Windows explicitly tells us the result is numeric clipping. macOS doesn't promise a nice perceptual gamut compressor at the ColorSync layer either. ([learn.microsoft.com][2])

A good confidence hierarchy is:

```text
exact/reliable target primaries
    Windows AdvancedColorInfo
    Wayland preferred target_primaries
    trustworthy parametric/mac profile characterization

known contained named gamut
    macOS canRepresent(P3) -> Display P3

otherwise
    BT.709
```

BT.709 is conservative, but it is predictably correct. You can expose “target gamut confidence” diagnostically and improve it later without changing the rendering model.

## Validation

The best regression test is specifically a color that proves “BT.709 coordinate basis ≠ BT.709 gamut.”

For example, a linear Display-P3 red expressed in a linear BT.709/sRGB basis is approximately:

```text
[ 1.22494, -0.04206, -0.01964 ]
```

That is exactly why scRGB's extended coordinates matter.

On a P3 target, render a tagged P3-red patch. After libplacebo, before OS presentation, the SunPlayer FP16 video surface should retain a value close to that extended coordinate—not collapse toward `[1, 0, 0]`. With a BT.709 target, the same source should be gamut-mapped into BT.709. A BT.2020-red test is even more aggressive:

```text
[ 1.66049, -0.12455, -0.01815 ]
```

Then validate neutral greys independently; changing only target gamut must not tint D65 neutrals.

For platform-level validation, capture SunPlayer's pre-OS FP16/PQ surface first, because that tells you whether your pipeline is mathematically correct. Then do a physical display check with P3-inside-but-709-outside patches. Screenshots are unreliable evidence because platforms differ on where screenshot capture occurs relative to color management. A colorimeter is the actual end-to-end test.

On Windows specifically, run the same vectors under HDR AC and WCG AC. Chromaticity should stay consistent, while only HDR gets `W/80`. Change the Windows SDR-white slider: the video tone-map target should rerender because `P/W` changed, and the final compositor scale should change exactly once. Under WCG SDR, that slider concept does not apply and final scale remains one. ([Microsoft Learn][1])

## So: how much is already done?

Quite a lot.

The source → libplacebo → SDR-white-relative FP16 composition architecture is right. The `203 × headroom` virtual target is right for the policy you've chosen. The Windows HDR `W/80` stage is right. macOS's display-relative `1.0` and current EDR-headroom observation are right. Wayland already has target luminance/reference-white and even parses target primaries. And your OS/compositor calibration ownership decision is right.

The main work left is much narrower than “redo color management”:

**propagate a real target gamut into `target.color.hdr.prim`; represent Windows HDR/WCG/ordinary SDR distinctly; obtain a safe Mac target gamut; stop discarding Wayland target primaries; and decide whether managed Wayland's final image description should advertise SunPlayer's already-mapped target volume.**

The one other caveat for eventually saying “everything color-correct” is source ICC: SunPlayer currently deliberately strips source ICC from the render-local libplacebo frame, so arbitrary ICC-profiled RGB media remains an explicit unsupported corner even after display gamut is fixed.

### HDR Advanced Color

This is basically what SunPlayer already does, minus the target gamut.

Windows' HDR composition space is scRGB/extended-linear BT.709. It is scene-referred: numeric `1.0 = 80 nits`. Microsoft explicitly says an Advanced-Color-aware app should use `AdvancedColorInfo` for the target display characteristics, and that it provides native RGB primaries, white point, min/max luminance, full-frame luminance, and current SDR-white luminance. ([Microsoft Learn][1])

So SunPlayer's intended libplacebo target should be roughly:

```cpp
target.color.primaries = PL_COLOR_PRIM_BT_709;
target.color.transfer = PL_COLOR_TRC_LINEAR;

// raw xy from AdvancedColorInfo:
target.color.hdr.prim = windowsNativePrimaries;

target.color.hdr.max_luma =
    PL_COLOR_SDR_WHITE * (P / W);

target.color.hdr.min_luma =
    PL_COLOR_SDR_WHITE * minNits / W;
```

The first line remains BT.709 because that's the **coordinate system** of the FP16 texture. `hdr.prim` becomes the **gamut libplacebo should fit the video into**. Current SunPlayer lacks that final assignment, so inference turns it into BT.709 gamut today.

Then your final compositor does exactly:

```text
output scRGB = composedWorkingRGB × W / 80
```

because SunPlayer's working `1.0 = W`, whereas Windows HDR scRGB `1.0 = 80 nits`.

That existing calculation is conceptually right. `PresentationTarget` already calculates `sdrScale = W / 80` when the swapchain is scene-referred.

And importantly: **do not ask Windows to tone-map this again.** SunPlayer/libplacebo maps to `P/W` because otherwise DWM's handling at the physical limit is essentially clipping, which is precisely the ugly behavior you've already observed.

### And yes, display ICC works here

This part is nice.

When Advanced Color is active, Windows says it performs **automatic system color management**. It converts from the color space tagged by the application to the display-referred color space defined by the display's colorimetry and current calibration/profile. If no display profile exists, Windows falls back to EDID colorimetry. Microsoft explicitly recommends that Advanced-Color-aware apps **stop directly accessing the display ICC profile**. ([Microsoft Learn][2])

So this would be wrong:

```text
libplacebo
→ display ICC
→ scRGB
→ Windows Advanced Color
→ display ICC again
```

The correct division is:

```text
libplacebo:
    source → display color VOLUME

Windows:
    abstract scRGB coordinates → calibrated physical display
```

Those are different operations.

Even better, `AdvancedColorInfo` isn't necessarily just raw EDID garbage. Microsoft's hardware calibration pipeline can take display information from an MHC ICC profile; MHC information is treated as a high-trust source and can override EDID/driver information, and Windows exposes the resulting best-known display characteristics through its HDR/Advanced Color capability APIs. ([Microsoft Learn][3])

So if the display has a proper Windows Advanced Color calibration profile:

```text
ICC/MHC calibration
        ↓
    Windows
        ├─ uses calibration internally
        └─ gives SunPlayer resulting target characteristics
                   ↓
             AdvancedColorInfo
                   ↓
             libplacebo hdr.prim / luminance
```

That's basically ideal. SunPlayer doesn't need an ICC parser for the monitor.

One caveat: Windows distinguishes profile associations intended for normal/SDR operation (`STANDARD`) from HDR (`EXTENDED`). A classic SDR profile isn't automatically the HDR calibration profile just because it exists; the appropriate profile association has to exist for the current Advanced Color mode. ([Microsoft Learn][2])

### Windows WCG / SDR Advanced Color

This needs a small but important change to SunPlayer's current state model.

Windows has three actual values:

```cpp
AdvancedColorKind::StandardDynamicRange
AdvancedColorKind::WideColorGamut
AdvancedColorKind::HighDynamicRange
```

WCG and HDR both use FP16/scRGB composition, but they have different luminance semantics. ([Microsoft Learn][4])

For WCG SDR:

```text
scRGB 1.0 = display reference white
not 80 nits
```

Windows explicitly calls it **display-referred**. HDR is scene-referred and uses 80 nits. ([Microsoft Learn][5])

So for WCG:

```text
target gamut      = AdvancedColorInfo native primaries
target headroom   = 1.0
final SDR scale   = 1.0
Windows ICC       = yes, system-owned
```

HDR video gets tone-mapped down to SDR luminance while retaining the monitor's wider chromatic gamut.

That means something like a P3 red can still produce scRGB coordinates such as:

```text
[1.225, -0.042, -0.020]
```

even though luminance headroom is only `1.0`. Extended RGB components are not equivalent to HDR brightness.

Your current Windows provider unfortunately destroys this distinction:

```cpp
state.hdrActive =
    colorInfo.CurrentAdvancedColorKind()
        == AdvancedColorKind::HighDynamicRange;
```

and doesn't retain `WideColorGamut` at all. It also isn't copying `RedPrimary`, `GreenPrimary`, `BluePrimary`, or `WhitePoint`.

So for Windows I think the immediate state fix is pretty obvious: retain the actual `AdvancedColorKind`, plus native raw primaries/white point.

There is another current issue around this: `PresentationTarget` only considers Windows display data usable when `display.hdrActive` is true.  That means a managed WCG display currently won't contribute its display target correctly.

### Normal Windows SDR, no Advanced Color

Here ICC is unfortunately different.

Microsoft explicitly says that when Advanced Color is **inactive**, Windows does not automatically color-manage ordinary DirectX output. It effectively assumes the application's output is sRGB. For accurate output on a calibrated monitor, a traditional application has to obtain and apply the display ICC transform itself. ([Microsoft Learn][2])

So:

```text
AdvancedColorKind::StandardDynamicRange

SunPlayer:
    target gamut = BT.709/sRGB
    headroom = 1
    final output = ordinary sRGB

Windows:
    no guaranteed application→display ICC conversion
```

That's the one mode where "let Windows handle the ICC" isn't sufficient.

For V1, your existing `UnmanagedSrgb` fallback is reasonable: don't pretend you're calibrated when Windows isn't giving you a managed pipeline.

If we later want **fully color-correct legacy SDR Windows**, that's when SunPlayer needs:

```text
video + UI + subtitles
       ↓
complete composed linear surface
       ↓
display ICC transform
       ↓
SDR swapchain
```

Crucially, ICC belongs **after composition**, not inside the video libplacebo renderer, because UI and subtitles need the same calibration.

### What about source ICC?

Different ICC entirely.

For something like a JPEG/PNG/RGB source carrying an embedded ICC profile, yes, libplacebo can conceptually handle that on the **input** side. Its renderer supports an `image->icc`; if present, libplacebo uses it to decode the source and overrides corresponding scalar source colorspace information with the profile's characterization.

But SunPlayer currently intentionally does:

```cpp
effectiveSource.icc = nullptr;
effectiveSource.profile = {};
```

And your custom libplacebo build explicitly has:

```cmake
-Dlcms=disabled
```

So **source ICC currently does not work in SunPlayer**, by deliberate policy.

I wouldn't mix that work into this Windows display-gamut fix. For normal YUV video, matrix/transfer/primaries/HDR metadata are the normal source-color description anyway. Later, enabling source ICC for well-defined SDR RGB content is sensible; I'd keep weird combinations like PQ/HLG + ICC out until their precedence is explicitly decided.

So, Windows-only, I think the target architecture is now pretty solid:

```text
HDR Advanced Color
    libplacebo target = native gamut + P/W headroom
    final             = scRGB × W/80
    display ICC       = Windows

WCG Advanced Color
    libplacebo target = native gamut + 1.0 headroom
    final             = scRGB, no scale
    display ICC       = Windows

Standard SDR
    libplacebo target = BT.709 + 1.0 headroom
    final             = sRGB
    display ICC       = not automatically handled
```

And for the first two, **`AdvancedColorInfo` should be the sole Windows display-target API**. It already gives us exactly the primaries we're missing, and it abstracts the ICC/EDID/calibration mess underneath. That's significantly cleaner than touching display profiles ourselves. Yes — and the important thing is that **80 nits is not the right notion of “SDR display peak.”** It should not be treated as such.

Windows can report physical luminance capability even for SDR displays. `DXGI_OUTPUT_DESC1` exposes `MinLuminance`, `MaxLuminance`, and `MaxFullFrameLuminance`, and Microsoft explicitly says this information is useful and available for both HDR and SDR displays and should be used for tone/gamut mapping. The values generally come from EDID or an override/profile. ([Microsoft Learn][1]) `AdvancedColorInfo` likewise exposes max/min/full-frame luminance and primaries. ([Microsoft Learn][2])

But there is a catch: those are basically **display capabilities**, not necessarily “the panel is currently emitting 137 nits because the user set brightness to 42%.” `MaxLuminance` is documented as the maximum luminance the display is capable of rendering. ([Microsoft Learn][3])

So there are really three quantities:

```text
reported panel max       e.g. 350 nits
current physical white   e.g. 140 nits because brightness=40%
SDR code white           RGB 1.0
```

For an SDR display, Windows defines the last one **display-relatively**:

```text
RGB 1.0 = display white
```

not 80 nits. Microsoft explicitly contrasts it with HDR:

```text
SDR: 1.0 = display reference/max white
HDR: 1.0 = 80 nits
```

and says the Windows SDR reference-white concept applies only to HDR displays. ([Microsoft Learn][4])

So for Windows SDR, we should not do anything like:

```text
output *= 80 / displayMax
```

or pretend the monitor has an 80-nit maximum.

### What the 80 currently means in SunPlayer

In the current code, that `80.0f` is mostly a fallback semantic anchor:

```cpp
float sdrWhiteNits = 80.0f;
```

But SDR presentation modes already clamp target headroom to exactly `1.0`.  So it isn't saying:

> this SDR monitor peaks at 80 nits.

For a normal SDR output, the meaningful contract should just be:

```text
working white 1.0
    ↓
sRGB white 1.0
    ↓
whatever physical luminance the monitor currently produces for white
```

I would actually avoid exposing `80 nits` diagnostically in that mode because it's misleading.

### Can we know the actual current SDR white?

Not reliably for every Windows monitor.

For an external monitor, Windows has DDC/CI APIs such as `GetMonitorBrightness`, but that returns a monitor brightness setting, not calibrated luminance in nits. Microsoft also explicitly warns that many monitors implement the VESA controls poorly and doesn't recommend blindly relying on them. ([Microsoft Learn][5])

Internally, Windows' display-driver brightness interface can operate in actual calibrated millinits when the OEM supplies calibrated brightness data. Windows even has a `NitsCalibrated` capability bit. ([Microsoft Learn][6]) But that's driver infrastructure; there isn't a clean universal desktop-app API I'd want SunPlayer's color correctness to depend on.

So, for plain SDR:

```text
DXGI MaxLuminance ≈ panel capability
actual current white ≠ reliably known
```

Especially with laptop brightness controls, monitor OSD brightness, ambient-light adaptation, eco modes, etc.

### Does SunPlayer actually need current SDR nits?

For the **normal relative SDR playback policy**, I think: **no**.

If we're outputting an SDR surface, the desktop itself is relative. White is white. SunPlayer should tone-map into:

```text
black → 0
display white → 1
headroom → 1
```

The display then determines how many physical nits `1.0` currently means.

This is actually the cleanest behavior for a desktop application: your video white tracks the rest of the desktop instead of SunPlayer trying to produce an absolute 100-nit patch while every other app's white is 250 nits.

And this means the existing SDR target:

```text
headroom = 1
```

is fundamentally sensible.

### Where physical SDR nits could matter

There is a more “reference-ish” alternative for HDR→SDR tone mapping:

> Tone-map the HDR movie specifically for a 100-nit / 120-nit / 200-nit SDR viewing environment.

That's a different policy.

For example, a monitor might advertise 400 nits but currently be set to about 120 nits. If we blindly tell a physically anchored HDR mapper “400-nit SDR target,” that is arguably *worse* than not knowing.

So I would distinguish:

**Normal playback**

```text
SDR target = relative display white
headroom = 1
no user nit setting necessary
```

**Optional reference/advanced mode**

```text
SDR target white = user-defined physical luminance
e.g. 100 / 120 / 160 / 200 nits
```

That second one would make sense as an advanced option eventually.

### What should we do with DXGI's SDR nit data, then?

Still collect it.

I'd have Windows report:

```text
reportedMinNits
reportedMaxNits
reportedFullFrameMaxNits
nativePrimaries
whitePoint
AdvancedColorKind
```

for SDR and HDR whenever valid. Microsoft specifically recommends the quantitative data for tone/gamut decisions on both types of display. ([Microsoft Learn][4])

But distinguish it semantically:

```text
HDR:
    W = SdrWhiteLevelInNits
    P = reported usable peak
    headroom = P / W
    actual output scale = W / 80

SDR Advanced Color:
    headroom = 1
    1.0 = display white
    reportedMaxNits = capability/diagnostic
    no /80 scaling

ordinary SDR:
    headroom = 1
    1.0 = assumed sRGB display white
    reportedMaxNits = capability/diagnostic if available
    no /80 scaling
```

`SdrWhiteLevelInNits` should really be considered an **HDR-only reference-white input** in our policy. Microsoft's Win32 documentation for `DISPLAYCONFIG_SDR_WHITE_LEVEL` literally defines it as SDR white *within an HDR monitor*. ([Microsoft Learn][7])

So I would **not add a user-configurable SDR nit value to normal playback yet**. I would first fix the state model so 80 disappears as a fake-looking SDR display value, collect actual reported SDR luminance capability, and continue treating SDR output as display-relative.

A later setting like **“SDR tone-mapping target: Auto / 100 nits / 120 nits / …”** could be useful, but that would deliberately opt into a physically anchored/reference mode rather than fixing a deficiency in the normal Windows SDR pipeline.
